Live migrations

Changing a database while it serves traffic.

Jonas WeberPlatform team

Hello, I am Jonas from the platform team. Over the last year we changed the schema of our biggest table three times without taking the service down. Today I will show the pattern we use, the one mistake that nearly broke it, and the numbers from the third migration. You can stop me at any point.

The problem

Every migration is a bet on the order of events.

Old code and new code run side by side during any deploy, sometimes for minutes. A migration that assumes one version at a time is a bet that nothing overlaps. Production always overlaps. So the question is not how to make the change fast. It is how to make every intermediate state safe for both versions.

The pattern

Expand, migrate, contract

Step 1

Expand

Add the new column.

Step 2

Migrate

Copy data, dual-write.

Step 3

Contract

Drop the old column.

The pattern has three phases and each one is a separate deploy. Expand adds the new structure and changes nothing else. Migrate backfills the data and writes to both places. Contract removes the old structure only after nothing reads it. Each phase can be rolled back on its own, which is the whole point.

Migrate

Write to both, read from one

The application writes every change to both columns. Reads still come from the old one, so nothing visible changes. A backfill job copies history into the new column. When counts and checksums match, a flag switches reads to the new column. If something looks wrong, flip the flag back; no data is lost on either side.

Backfill

Copy in small, boring batches

UPDATE orders
SET    total_cents = ROUND(total * 100)
WHERE  id BETWEEN :from AND :to
  AND  total_cents IS NULL;
-- 5,000 rows per batch, sleep 50 ms between batches

Idempotent: running a batch twice changes nothing.

This is the whole backfill. It updates a fixed range of ids and only touches rows that are still empty, so it can be stopped and restarted at any time. We run five thousand rows per batch and pause briefly between batches to keep replication lag low. The simplicity is deliberate. Clever backfills are where outages come from.

Zero minutes of downtime, nine days from the first deploy to the last, and three times we flipped the read flag back. Those rollbacks are a feature, not a failure: each one took seconds and each one found a real bug in the new read path before customers did. The incident log is linked in the slides.

Lessons

What we would tell ourselves

  • Ship each phase as its own deploy
  • Verify with checksums, not row counts
  • Keep the rollback a flag, not a deploy
Three lessons. First, never combine phases in one deploy, because the combination removes the safe intermediate states. Second, verify the backfill with checksums over sampled ranges; matching row counts hide wrong values. Third, make the rollback a runtime flag. A rollback that needs a deploy is too slow to be a safety net.
